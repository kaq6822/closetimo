- 진단 스크립트·로그·현재 위젯 렌더는 `build/ui_review_20261014/`에 보관했다. 이 경로는 Git 추적 대상이 아니다. 실행: `flutter test --no-pub build/ui_review_20261014/ui_review_probe_test.dart --reporter expanded`.

## 전체 판단

따뜻한 배경, 세이지 색상, 둥근 카드의 방향은 일관된다. 현재 완성도를 떨어뜨리는 부분은 실제 데이터와 이동 결과의 불일치, 콘텐츠보다 큰 상단·사진 영역, 기능을 암시하지만 반응하지 않는 UI, 부족한 상태 안내다. 새 장식보다 아래 순서로 보완하는 편이 효과가 크다.

P1은 잘못된 데이터 변경·목록 결과·주요 컨트롤 잘림, P2는 주요 사용 흐름과 신뢰·조작성, P3는 발견성·문구·마감 개선으로 분류했다.

## 우선 수정 후보

### UI-01 · P1 · 바구니에서 제외한 옷이 선택 상태에 남음 — 신규, 재현 확인

**재현**: 바구니의 옷을 체크 → 그 옷의 상세에서 바구니 제외 → 세탁 화면 복귀. 목록은 비어도 선택 ID가 남아 완료 버튼이 활성화된다. 버튼을 누르면 이미 제외한 옷에 세탁 날짜와 세탁 이벤트가 기록된다. 삭제한 옷의 ID가 남는 경우에는 실제 처리 수와 토스트 수가 달라질 수 있다.

**근거**: [세탁 화면](../../../lib/features/laundry/laundry_screen.dart#L67)은 `selection` 전체를 사용하고, [선택 provider](../../../lib/features/laundry/laundry_selection_provider.dart)는 목록 변경과 동기화되지 않는다. [완료 처리](../../../lib/data/repositories/isar_laundry_repository.dart#L36)는 대상의 `inLaundry` 여부를 확인하지 않는다. 진단에서 빈 목록·선택 `{1}`·활성 버튼·세탁 이벤트 1건을 확인했다.

**제안**: 현재 바구니 ID와 선택 ID의 교집합으로 버튼·선택 수·완료 대상을 계산하고 사라진 선택을 정리한다. repository에서도 현재 바구니에 있는 항목만 처리하며, 토스트는 실제 처리 수를 표시한다.

**검증 기준**: 제외·삭제·외부 완료로 항목이 사라지면 선택도 제거된다. 빈 바구니에서 완료 버튼이 비활성이고 제외한 옷의 날짜·이벤트가 바뀌지 않는다.

### UI-02 · P1 · 홈 ‘기타’의 숫자와 이동한 목록이 다름 — 신규, 재현 확인

**재현**: 신발과 가방만 등록하면 홈 ‘기타’는 2점이지만, 카드 탭 후 옷장은 빈 결과가 된다.

**근거**: [홈 집계](../../../lib/data/repositories/isar_item_repository.dart#L110)는 `homeBucket`을 사용하지만, [카드 이동](../../../lib/features/home/widgets/category_bento.dart#L66)은 `category=etc`를 전달하고 [옷장 필터](../../../lib/data/repositories/isar_item_repository.dart#L69)는 정확히 `Category.etc`인 옷만 고른다. production 집계·필터 실행 결과가 각각 2점·0점이었다. FR-019와 ‘기타’ 버킷 정의를 함께 충족해야 한다.

**제안**: 홈의 합산 ‘기타’와 옷장의 개별 ‘기타’를 구분하는 필터 계약을 정의한다. 홈 카드는 신발·가방·원피스·액세서리·운동복·기타 전체로 연결하고, 사용자가 합산 필터임을 알 수 있는 라벨을 제공한다.

**검증 기준**: 홈 카드의 집계 범위와 이동한 목록의 범위가 일치한다. 옷장 ‘기타’ 칩의 개별 카테고리 의미도 유지한다.

### UI-03 · P1 · 작은 화면·큰 글자에서 버튼과 카드가 넘침 — 신규, 재현 확인

**재현**: 논리 화면 320×568, `TextScaler.linear(2)`.

- ‘선택 항목 세탁 완료 처리’ 버튼: 오른쪽으로 약 86px overflow.
- 홈 카테고리 카드: 각 카드가 아래로 약 50px overflow하며 라벨이 다음 카드 영역으로 내려간다.

**근거**: [PrimaryButton](../../../lib/core/widgets/primary_button.dart#L40)의 라벨은 `Row` 안에서 너비 제약 없이 배치된다. [카테고리 카드](../../../lib/features/home/widgets/category_bento.dart#L24)는 고정 `childAspectRatio`로 높이를 정하지만 글자는 커진다. 재현 이미지: `build/ui_review_20261014/laundry_cta_320_scale2.png`, `home_categories_320_scale2.png`.

**제안**: 완료 버튼을 ‘선택한 2점 세탁 완료’처럼 간결하게 만들고 라벨의 줄바꿈·높이 증가를 허용한다. 카드도 글자 배율에 따라 높이 또는 열 수를 조정한다. 사용자 글자 확대를 차단하는 방식은 피한다.

**검증 기준**: 320·393px 너비와 글자 1·1.3·2배 조합에서 주요 컨트롤의 잘림·겹침이 없다.

### UI-04 · P2 · 미구현 기능을 실제 기능처럼 안내 — 기존 F-06, 코드상 잔존 확인

[설정](../../../lib/features/settings/settings_screen.dart#L90)의 ‘데이터 백업’·‘개인정보 처리방침’·‘앱 정보’에는 이동 화살표가 있지만 탭 동작이 없다. [등록 안내](../../../lib/features/add_item/add_item_screen.dart#L306)는 세탁 알림 발송을 약속하지만 spec은 v1에서 토글 저장만 지원한다.

**제안**: 알림 안내를 ‘설정한 횟수에 도달하면 세탁 필요로 표시해요’로 맞춘다. 구현 전 설정은 숨기거나 ‘준비 중’으로 명시하고, 실제 목적지가 없는 행에서는 화살표를 제거한다. 알림 토글의 실제 발송 범위를 명확히 표시한다. 백업·알림 구현을 선택한다면 별도 spec이 필요하다.

## 정책·spec 정리가 필요한 항목

- 착용 기록 후 상세 유지: 코드상 잔존하며 기존 F-05다. 현재 동작은 갱신된 카운터를 바로 확인할 수 있어 UX상 이점이 있다. ‘직전 화면으로 복귀’라는 spec·라우트 계약과 맞출지, 상세 유지로 요구사항을 갱신할지 결정한다. 문서 차이만으로 자동 복귀를 복원할 필요는 없다.
- 홈 ‘관리 필요’: 현재 dirty 수이고 세탁 바구니 수와 다르다. 수동으로 바구니에 담은 깨끗한 옷은 포함되지 않는다. 집계 정책을 바꾸기 전에 ‘세탁 필요’와 ‘바구니 대기’를 별도로 명확히 설명하는 방법을 검토한다.
- 가로 화면: 기존 F-10은 아직 정책 결정 대상이다. 세로 전용을 선택하면 제품·플랫폼 설정과 spec을 함께 맞추고, 가로 지원을 선택하면 가로 배치도 검증한다. 이번 검토에서는 새 가로 기기 실행을 하지 않았다.
