## 0. 요약

- 지금 앱의 불편은 **기능이 없어서가 아니라 "입력이 타이핑 중심"이고 "매일 하는 일이 홈에 없어서"** 생긴다.
  등록·착용·세탁 기능은 갖춰졌지만, 옷을 찾게 해 주는 단서(색상·계절·세부 종류)를 사용자가 직접 써야 하고,
  가장 자주 하는 "오늘 입은 옷 기록"은 옷장 탭의 길게 누르기 또는 상세 화면 안에 있다.
- 방향은 세 가지다. **① 입력은 고르기로, 고르기는 사진에서 자동 제안으로 ② 매일 하는 일은 홈에서 1~2탭 ③ 사진이 곧 데이터**.
- 온디바이스 AI는 **실제로 이 Mac에서 돌려 보고** 판단했다.
  - **채택**: 순수 Dart 색상 추출(전 기기), Apple Vision 배경 제거(iOS 17+).
  - **보조 힌트로만**: Apple Vision 이미지 분류(신발·가방·청바지·후드 등 일부만 신뢰 가능).
  - **선택 기능(사용자가 켬)**: Apple Foundation Models 이미지 입력(iOS 27 + Apple Intelligence 기기). 현재 툴체인(Xcode 26.6)으로는 빌드 불가.
  - **포기**: Samsung Galaxy AI(서드파티 공개 SDK 없음), Android ML Kit/Gemini Nano(진단 데이터를 Google로 전송 → 헌법 III 충돌).

## 1. 지금 불편한 지점 (코드·화면 근거)

| 상황 | 현재 | 왜 불편한가 |
|---|---|---|
| 처음 옷 20벌 넣기 | 등록 화면의 사진 카드가 첫 화면을 거의 다 차지하고 한 번에 1장. 사진만 넣으면 이름이 `이름 없는 옷` | 20번 반복. 목록에 `이름 없는 옷`이 줄지어 쌓여 구분이 안 된다 |
| 옷에 정보 붙이기 | 종류 9개 + 용도 1개(`운동`) + 자유 태그(접힘, 직접 타이핑) | 색상·계절·세부 종류를 매번 타이핑해야 해서 사실상 안 쓰게 되고, 그래서 검색·필터도 쓸모가 없다 |
| 오늘 3벌 입음 | 홈에는 기록 버튼이 없음. 옷장 → 길게 눌러 선택 모드 → 3벌 선택 → 착용 기록 → 시트 확정 | 매일 하는 핵심 행동이 숨은 제스처 뒤에 있다 |
| 홈 화면 | 인사말 + 전체/깨끗/관리 필요 숫자 + 아우터/상의/하의/그 외 개수 | 숫자를 보여 줄 뿐 다음 행동으로 이어지지 않는다 |
| 옷장 그리드 | 타일마다 `착용 횟수 0/6 · 마지막 세탁 —` 텍스트, 사진은 배경 포함 | 옷장 앱인데 사진보다 관리 숫자가 먼저 보인다 |
| 세탁 | 바구니 목록 + `선택 항목 세탁 완료 처리`. 안내 문구는 `'세탁 중' 또는 '오염됨'`(실제 상태명은 `관리 필요`) | 실제로는 흰옷/색깔옷/드라이를 나눠 빤다. 앱이 그 분리를 도와주지 않는다 |
| 설정 > 알림 | `알림 발송은 준비 중이에요` 토글 3개 | 동작하지 않는 설정이 노출되어 있다 |

## 2. 제안 기능

우선순위: **P0** = 이번 개편의 핵심, **P1** = P0 직후, **P2** = 실사용 관찰 후.

### P0-A. 구조화 속성 — "태그를 타이핑"에서 "프리셋을 탭"으로

자유 태그는 유지하되, 옷 찾기에 실제로 쓰이는 축을 **프리셋 칩**으로 제공한다. 모두 선택 입력이다.

| 축 | 값(초안) | 입력 | 자동 제안 |
|---|---|---|---|
| 종류(기존) | 아우터·상의·하의·원피스·신발·가방·액세서리·기타·미분류 | 단일 | Vision 라벨(iOS, 일부) |
| **세부 종류** | 상의: 티셔츠·셔츠/블라우스·니트·맨투맨/후드·민소매·폴로 / 하의: 청바지·슬랙스·면바지·반바지·스커트·트레이닝 / 아우터: 코트·패딩·재킷·블레이저·점퍼·카디건·조끼 / 원피스: 원피스·점프수트 / 신발: 운동화·구두·부츠·샌들/슬리퍼·로퍼 / 가방: 백팩·숄더·토트·크로스·클러치 / 액세서리: 모자·머플러/스카프·벨트·장갑·양말·주얼리·시계·안경 | 단일, 종류에 종속 | FM(iOS 27, 선택) |
| **색상** | 검정·흰색·회색·아이보리·베이지·카멜·브라운·네이비·파랑·하늘·데님·초록·카키·빨강·버건디·분홍·보라·노랑·주황 (스와치로 표시) | 복수(최대 3) | **사진에서 추출(전 기기)** |
| **계절** | 봄·여름·가을·겨울 + `사계절` 단축 | 복수 | 세부 종류 기반 기본값(예: 패딩→겨울) |
| **용도/상황** | 데일리·출근·운동(기존)·외출/모임·여행·홈웨어·격식 | 복수 | — |
| 소재·패턴 | 면·니트/울·데님·가죽·린넨·기능성·캐시미어 / 무지·스트라이프·체크·도트·그래픽·플로럴 | 단일, 접힘 | FM(iOS 27, 선택) |
| 자유 태그(기존) | 사용자가 만든 값 | 복수 | — |

- **자동 이름**: 사진만으로 등록해도 `{색상} {세부 종류}`(예: `검정 니트`, `데님 청바지`)로 이름을 채운다. 둘 다 없을 때만 `이름 없는 옷`.
- **저장 방식**: 세부 종류·색상·소재·패턴은 **안정적인 문자열 코드**(`knit`, `black`)로 저장하고 한국어 라벨은 코드에서 매핑한다.
  ordinal enum과 달리 값 추가·순서 변경이 데이터를 깨지 않는다. 계절은 4값 고정이라 enum도 가능. 용도 `ItemPurpose`는 끝에만 추가한다.
- **영향**: `Item` 필드 추가(클래스 끝에), 백업 `formatVersion` 증가와 구버전 백업 읽기 호환, `TagRepository`·필터·검색 확장.

### P0-B. 빠른 등록 재설계 — "여러 장 고르고, 카드 넘기며 탭으로 분류"

1. `+` → **앨범에서 여러 장 선택**(`pickMultiImage`) 또는 **카메라 연속 촬영**.
2. 사진마다 **분류 카드**가 한 장씩 뜬다. 큰 사진(배경 제거본) 아래에
   종류 → 세부 종류 → 색상(**자동 제안이 미리 선택된 상태**) → 계절 칩만 있다. 탭만으로 끝난다.
3. `다음`을 누르면 저장하고 다음 카드로 간다. `건너뛰기`는 미분류로 저장한다.
4. 브랜드·구매일·가격·세탁 방법·관리 주기는 **나중에 상세에서** 채운다(현재 "추가 정보" 접힘 유지).
5. 중간에 나가도 처리하지 않은 사진은 "정리 대기"로 남아 홈에서 이어서 할 수 있다.

목표: 사진 10장 → 분류 완료까지 **1장당 탭 4~5회, 타이핑 0회**(현재는 1장당 화면 진입·사진 선택·이름 타이핑·저장).

### P0-C. 홈을 "오늘" 중심으로

위에서부터 다음 순서로 배치한다.

1. **오늘 입은 옷** — 자주·최근 입은 옷 썸네일 가로 목록. 여러 개를 탭해 고르고 `기록` 한 번. (어제/날짜 변경은 기존 시트 재사용)
2. **세탁** — `바구니 5점 · 흰옷 2 / 어두운 옷 3` + `세탁 완료` 바로가기. 관리 필요 옷이 있으면 `바구니에 담기` 제안.
3. **정리 대기** — 분류하지 않은 사진 N장(P0-B). 0이면 숨긴다.
4. **이번 주 제안** — 계절이 바뀔 때 `여름 옷 12벌 보관할까요?`, 60일 이상 안 입은 옷.
5. 현재의 통계·종류 카드는 맨 아래로 내리고 압축한다.

### P1-D. 옷장 탐색

- **패싯 필터 시트**: 종류›세부 종류, 색상 스와치, 계절, 용도. 같은 축은 OR, 다른 축은 AND. 결과 수를 미리 보여 준다.
- **이번 계절** 빠른 필터(현재 월 기준), 기존 `입을 수 있음`과 함께 상단 고정.
- **사진 중심 그리드**: 3열/2열 밀도 전환, 타일 텍스트는 이름 1줄 + 상태 점 하나. 관리 숫자는 상세로 옮긴다.

### P1-E. 세탁 — 색 분리를 도와주는 바구니

- 바구니를 색상·관리 방법으로 자동 그룹: **흰색·밝은색 / 어두운색 / 데님 / 손세탁·드라이**(색상 미지정은 "분류 안 됨").
- 그룹 헤더에서 그룹 전체 선택 → `세탁 완료`. 안내 문구를 실제 상태명(`관리 필요`)에 맞춘다.

### P1-F. 코디와 착용 캘린더

- 자주 입는 조합을 **코디**로 저장하고 한 번에 기록(내부적으로는 옷별 wear 이벤트). 자유 배치 캔버스는 만들지 않는다.
- 월 캘린더에서 날짜별로 입은 옷 썸네일을 본다(OOTD 일기). 날짜를 탭해 그날 기록을 추가·수정한다.

### P1-G. 로컬 알림을 실제로 동작시키거나 숨긴다

- `flutter_local_notifications`로 기기 안에서만 예약한다(네트워크 없음): 매일 기록 리마인더(사용자 지정 시각), 바구니 N점 이상.
- 구현하지 않을 경우 설정에서 토글을 숨긴다.

### P2

- 착용당 비용(구매가 입력 시), 많이/안 입은 옷 순위, 계절 전환 도우미(계절 속성으로 일괄 보관·꺼내기).
- 홈 화면 위젯(iOS WidgetKit / Android App Widget)으로 "오늘 입은 옷" 1탭 기록.

## 3. 온디바이스 AI 조사·검증

### 3.1 로컬 실측 (2026-11-02, MacBook Apple Silicon, macOS 26.6)

Wikipedia 문서의 대표 이미지 11장(블레이저·카디건·셔츠·핸드백·후드·청바지·스커트·스니커즈·스웨터·티셔츠·트렌치코트)으로 측정했다.
제품 사진 4~5장과 착용 사진 6~7장이 섞여 있다. 맥에서의 수치이며 실기기 수치는 아니다.

**Apple Vision 배경 제거** (`VNGenerateForegroundInstanceMaskRequest`, iOS 17+)

- 11/11장에서 피사체를 분리했다. 첫 호출 507ms(모델 로드), 이후 23~30ms.
- 제품 사진(청바지·스니커즈·셔츠·가방)은 깔끔하다. 착용 사진은 **옷이 아니라 사람 전체**를 분리한다.

**Apple Vision 이미지 분류** (`VNClassifyImageRequest`, iOS 13+, 라벨 1,303개)

- 옷 관련 라벨: `jeans`, `hoodie`, `jacket`, `suit`, `shoes`/`sneaker`/`boot`/`sandal`, `bag`/`backpack`, `hat`, `scarf`, `glove`, `sock`, `sunglasses`, `jewelry`, `watch`, `swimsuit` 등.
  **`shirt`·`t-shirt`·`sweater`·`skirt`·`pants`·`coat`·`dress`(일반)는 라벨에 없다.**
- 결과: 청바지 `jeans 0.94`, 스니커즈 `sneaker 0.90`, 후드 `hoodie 0.91`은 정확. 티셔츠 착용 사진은 `jeans 0.87`(하의를 인식),
  스웨터·스커트·셔츠·코트는 옷 종류를 맞히지 못했다. 6~29ms.
- 판단: **신뢰도 높은 일부 라벨만 종류 제안에 쓰는 보조 힌트**. 상의 세부 종류 판별에는 쓸 수 없다.

**순수 Dart 색상 추출** (`image` 패키지로 64px 축소 → CIELAB k-means(k=4) → 19색 팔레트 최근접, 비중 15% 이상만)

| 사진 | 결과 | 평가 |
|---|---|---|
| 청바지(제품) | 데님 63%, 하늘 31% | 정확 |
| 스니커즈(제품) | 검정 45%, 빨강 27%, 흰색 17% | 정확 |
| 드레스 셔츠(제품) | 아이보리 95% | 정확 |
| 핸드백(제품) | 브라운 45%, 베이지 39%, 카멜 15% | 정확 |
| 후드(착용) | 검정 61%, 회색 20% | 대체로 정확(재킷 포함) |
| 티셔츠(착용) | 검정 32%, 빨강 32%, 베이지 26% | **피부·머리·바지가 섞임** |

- 5~65ms, 모든 기기에서 동작, 의존성은 `image` 패키지(순수 Dart)뿐.
- 판단: **채택**. 배경 제거본(iOS 17+)이나 단독 제품 사진에서 정확하다. 착용 사진은 오차가 크므로
  **미리 선택된 제안 칩**으로만 보여 주고 사용자가 바로 고칠 수 있게 한다. 자동 확정하지 않는다.

**Apple Foundation Models** (기기 내 LLM)

- 이 Mac에서 `SystemLanguageModel.default.availability == available`, 지원 언어에 `ko` 포함을 확인했다.
- iOS 26의 Foundation Models는 텍스트만 받는다. **이미지 입력은 iOS 27(WWDC 2026 발표)에 추가**됐다.
  사진을 넣고 `@Generable` 구조체(세부 종류·소재·패턴·계절)로 받을 수 있어, Vision이 못 하는 상의 세부 종류 판별에 맞는 기술이다.
- 제약: Apple Intelligence 기기(iPhone 15 Pro 이상)에서 사용자가 Apple Intelligence를 켜고, 기기 언어가 지원 언어여야 한다.
  컨텍스트 4K 토큰이며 이미지도 토큰을 소비한다.
- **현재 개발 환경은 Xcode 26.6 / iOS SDK 26.5라 iOS 27 이미지 입력 API를 빌드할 수 없다.** Xcode 27로 올린 뒤
  실기기에서 정확도와 응답 시간을 측정해야 한다. 이미지 입력은 로컬에서 검증하지 못했다.
- 판단: **선택 기능**. 설정 `기기 내 AI로 자세히 분석`(기본 꺼짐, 미지원 기기에서는 숨김). 결과는 제안 칩으로만 쓴다.
  Private Cloud Compute 모델은 서버 처리이므로 쓰지 않는다.

| 기술 | 사실 | 판단 |

| Samsung Galaxy AI | 휴대폰용 서드파티 공개 SDK를 확인하지 못했다. Samsung Neural SDK는 서드파티 제공을 중단했다. "Galaxy AI Agent SDK"는 비공식 블로그 1건에만 나온다 | **직접 연동 포기**. 대신 갤러리의 피사체 잘라내기로 저장한 투명 PNG를 앨범에서 고르면 투명 배경을 유지해 쓰도록 지원한다(기기에서 동작 확인 필요) |
| ML Kit GenAI Prompt API (Gemini Nano) | 이미지+텍스트 입력, 한국어 검증 언어. 지원 기기는 Galaxy S26·Z Fold7/TriFold·Fold8/Flip8, Pixel 등 소수(S25는 이미지 설명 API만). 베타, 포그라운드에서만 동작 | **제외** — ML Kit은 GenAI를 포함한 모든 기능에서 기기 정보·앱 정보·성능 지표를 HTTPS로 Google에 보내며 끄는 설정이 문서에 없다. 헌법 III(외부 SDK·네트워크 금지)과 충돌 |
| ML Kit Subject Segmentation (배경 제거) | Play 서비스로 모델을 받고 위와 같은 진단 데이터 전송 | **제외**(같은 이유) |
| 앱에 모델 번들(LiteRT 등) | 분류·분할 모델을 직접 넣으면 전 기기 오프라인 동작. 앱 용량 증가와 모델·학습 데이터 라이선스(상업 이용) 확인 필요 | **이번 범위 제외**. 실사용에서 Android 배경 제거 요구가 크면 별도 검토 |

결과적으로 Android는 **색상 추출·자동 이름·프리셋 분류(전부 순수 Dart)** 로 iOS와 같은 등록 흐름을 쓰고,
배경 제거·AI 세부 분석만 iOS 전용 선택 기능이 된다.

### 3.3 구현 방식

- iOS: `ios/Runner`에 Swift `MethodChannel` 하나(`closetimo/vision`)를 직접 작성한다. 서드파티 Flutter 플러그인
  (`flutter_native_ai` 등 pre-1.0, 일부는 클라우드 라우팅 포함)은 쓰지 않는다.
- Dart 쪽은 `ImageAnalyzer` 인터페이스(`analyze(File) → AnalysisHints{subjectCutout?, colors, categoryHint?, details?}`)로 감싸고,
  플랫폼·OS 버전·사용자 설정에 따라 구현을 고른다. 실패하면 제안 없이 진행한다(등록을 막지 않음).
- 배경 제거본은 **원본과 별도로 저장**하고 상세에서 원본/배경 제거본을 전환할 수 있게 한다. 백업에 둘 다 포함한다.
- 테스트: 색상 추출은 고정 이미지로 단위 테스트, 플랫폼 채널은 fake 구현으로 feature 테스트, 실기기 E2E는 iOS 17+ 시뮬레이터.

## 4. 단계 제안

| 단계 | 범위 | 플랫폼 | 선행 조건 |
|---|---|---|---|
| 1 | P0-A 구조화 속성 + P0-B 빠른 분류 등록 + 색상 자동 제안 + 자동 이름 | iOS·Android | spec 005, 데이터 모델·백업 v3 |
| 2 | P0-C 홈 "오늘" + P1-D 패싯 필터 + P1-E 세탁 색 분리 | iOS·Android | 1단계 속성 |
| 3 | Apple Vision 배경 제거 + 분류 힌트 | iOS 17+ | 1단계 분석 인터페이스 |
| 4 | Foundation Models 이미지 분석(선택 기능) | iOS 27 + Apple Intelligence | Xcode 27, 실기기 |
| 5 | P1-F 코디·캘린더, P1-G 로컬 알림, P2 | iOS·Android | 사용 관찰 |

### 결정과 진행 (2026-11-02)

- 1~4단계를 모두 [spec 005](../../specs/005-attributes-quick-capture/spec.md)로 구현했다. 진행·남은 검증은
  [tasks.md](../../specs/005-attributes-quick-capture/tasks.md)를 따른다.
- 4단계(기기 내 AI)는 코드와 스키마까지 넣었지만 이미지 입력 호출은 iOS 27 SDK(Xcode 27)로 빌드할 때만 컴파일된다.
  지금 빌드에서는 설정이 보이지 않는다. Xcode 27 + Apple Intelligence 실기기 측정 전까지 미검증이다.
- 여러 장 등록은 장당 수 초가 걸리는 기기 내 AI를 쓰지 않고 빠른 분석(배경 제거·색상·분류 힌트)만 쓴다.
- Android 온디바이스 AI(ML Kit GenAI·Gemini Nano)는 사용자 결정에 따라 **사용자가 켜는 실험 기능으로 별도 검토**한다.
  진단 데이터 전송 때문에 헌법 III 예외 승인이 먼저 필요하다.

## 5. 기존 결정과의 관계

- 10-17 평가 계획은 "평가 전까지 태그 기본 접힘"이었다. 이번 제안은 자유 태그는 그대로 두고, **타이핑이 필요 없는
  프리셋 속성**을 노출하는 것이다. 사용자 요청(태그 확대·입력 간소화)에 따라 spec 005에서 이 결정을 갱신한다.
  평가 계획의 측정 항목(찾기 시간·입력 부담)은 프리셋 속성에 그대로 적용할 수 있다.
- 헌법 III: 위 채택 항목은 모두 기기 내 처리이며 네트워크 호출이 없다. ML Kit 계열은 이 원칙 때문에 제외했다.
