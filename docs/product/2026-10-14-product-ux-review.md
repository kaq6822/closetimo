# 실사용 관점의 제품·UX 검토 — 2026-10-14

## 판단 요약

현재 MVP는 한 벌의 등록 → 착용 기록 → 세탁 완료 흐름을 갖췄다. 다수 사용자의 지속 사용을 목표로 하면, **여러 벌을 반복 관리하는 데 드는 입력과 화면 이동을 줄이고, 기록을 놓치거나 잘못 입력해도 회복할 수 있게 하는 것**이 우선이다.

카테고리는 기본 탐색에 유효하다. 다만 현재 ‘종류’와 ‘용도’가 섞인 분류를 정리해야 한다. 태그는 검색·필터·일괄 편집에서 실제로 쓰일 때 추가할 가치가 있으며, 등록 폼의 입력 항목만 늘리는 방식은 피한다.

이번 검토의 기본 타깃은 현 MVP에 맞는 **개인용 옷장·세탁 관리 사용자**다. 코디·패션 콘텐츠 중심 사용자는 후속 타깃으로 구분했다. 우선 타깃에 대한 추가 답변 없이 진행한 가정이며, 제안은 확정된 feature spec이 아니다.

## 3. 카테고리와 태그의 실효성

### 현재 분류의 문제

현재 `Item`은 단일 `Category`를 가진다. `아우터·상의·하의·원피스·신발·가방·액세서리·운동복·기타` 중 하나만 선택한다. 자유 태그·색상·계절·용도 필드는 없으며 검색은 이름·브랜드만 대상으로 한다. [현재 모델](../../lib/data/models/item.dart), [검색·필터](../../lib/data/repositories/isar_item_repository.dart)

- **분류 축 혼합**: 운동용 티셔츠는 ‘상의’이면서 ‘운동용’이다. 운동용 바지는 ‘하의’이면서 ‘운동용’이다. ‘운동복’을 종류와 같은 단일 선택에 두면 종류별 탐색이나 용도별 탐색 중 하나를 포기한다.
- **큰 범주만 존재**: 상의가 많이 늘어나면 티셔츠·셔츠·니트를 한 그룹에서 찾아야 한다. 세부 종류는 실제 탐색 실패가 반복될 때 추가하되, 모든 사용자에게 처음부터 긴 분류표를 요구하지 않는다.
- **임의 기본값**: 새 옷의 기본 카테고리는 아우터다. 종류를 선택하지 않은 옷이 아우터로 집계된다. ‘미분류’는 아직 정리하지 않은 항목이고, ‘기타’는 기존 종류에 속하지 않는 항목이므로 의미를 구분한다.
- **홈 합산의 불일치**: 홈 ‘기타’는 원피스·신발·가방·소품·운동복까지 합산하지만 옷장 ‘기타’ 칩은 개별 `etc`다. 두 의미가 같은 라벨로 연결되는 문제를 먼저 고친다.
- **세탁을 고려하지 않은 포괄 범위**: 가방·액세서리까지 보유 목록에 넣을 수 있는 것은 유용하다. 다만 등록하면 반드시 매 N회 세탁하는 옷으로 취급되는 것은 별개 문제다. 분류와 관리 방식은 분리한다.

### 권장하는 최소 구조

| 정보 축 | 예 | 실사용 가치 | 권장 입력 방식 |
|---|---|---|---|
| 종류 | 상의, 하의, 아우터, 원피스, 신발, 가방, 소품 | 옷을 찾는 기본 출발점 | 대표 종류 1개. 미분류 허용 |
| 세부 종류 | 니트, 셔츠, 청바지 | 같은 종류가 많을 때 좁히기 | 선택 입력, 부모 종류에 종속. 탐색 수요 확인 후 |
| 계절 | 봄, 여름, 가을, 겨울 | 현재 계절에 맞는 옷 모으기 | 선택·복수 가능. ‘봄·가을’은 두 값 선택, ‘사계절’은 전체 선택 shortcut |
| 색상 | 검정, 흰색, 베이지 | ‘검정 상의’처럼 기억한 단서로 찾기 | 선택·소수 색상. 사진만으로 충분한 사용자에게 요구하지 않음 |
| 용도 | 운동, 출근, 여행 | 종류를 가로지르는 목적별 찾기 | 선택·복수 가능. ‘운동복’과 종류의 충돌 해소 |
| 관리 방법 | 기계세탁, 손세탁, 드라이, 미지정 | 같은 관리 방식의 옷 선택 | 일반 태그와 분리된 시스템 필드 |
| 관리·사용 가능 상태 | 바구니에 있음, 보관 중, 관리 권장 | 입을 옷과 관리할 옷 구분 | 행동/규칙과 연결된 시스템 상태. 자유 텍스트 태그로 대신하지 않음 |
| 위치·개인 분류 | 겨울 보관함, 회사 사물함 | 실제로 어디 있는지 자주 찾는 사용자에게 도움 | 후속 선택 기능. 기본 위치 입력을 강제하지 않음 |

예를 들어 ‘운동용 검정 티셔츠’는 **종류=상의, 용도=운동, 색상=검정**으로 검색할 수 있다. ‘세탁 바구니에 있음’은 태그가 아니라 실제 바구니 액션의 결과로 관리한다. 각 축은 필요한 것만 입력하며, 초기 화면에 이 표 전체를 그대로 폼으로 노출하지 않는다.

Indyx는 공식 안내에서 종류·브랜드·색상을 필터용 속성으로 소개하고, Whering은 사용자 태그와 일괄 편집을 안내한다. 공통적으로 참고할 점은 태그를 정보 장식이 아니라 탐색·편집에 연결하는 것이다. 이는 옷장이모에서의 효과에 대한 추론이며 실제 사용자 검증이 필요하다. [Indyx](https://www.myindyx.com/how-it-works), [Whering 태그](https://whering.co.uk/faq/my-stats-and-tags), [Whering 일괄 편집](https://whering.co.uk/faq/mass-edit-items)

### 자유 태그를 추가할 조건

다음이 함께 가능할 때 추가한다.

1. 옷 여러 벌에 한 번에 붙이거나 제거한다.
2. 기존 태그를 검색·재사용해 매번 새로 입력하지 않는다.
3. 이름 변경이 기존 옷 전체에 반영되고, 중복 태그를 합칠 수 있다.
4. 태그로 옷을 실제로 검색·필터링하며 선택 조건과 결과 수를 볼 수 있다.
5. 태그를 지워도 옷과 착용 기록은 남는다.
6. 사용하지 않아도 등록·착용·세탁의 핵심 흐름에 불이익이 없다.

필터는 예를 들어 `(상의 또는 하의) 그리고 여름 그리고 운동`처럼 같은 축의 복수 선택과 다른 축의 교집합을 구분해 보여준다. 자유 태그 간 ‘하나라도 포함/모두 포함’은 별도 정책으로 정의한다. 결과가 없으면 적용된 조건과 초기화 동작을 제공한다.

모든 태그를 필수로 입력하게 하거나 ‘출근/회사/오피스’ 같은 비슷한 태그를 계속 만들게 되면, 분류 체계를 유지하는 일이 새 관리 부담이 된다. 처음에는 종류를 정리하고 선택 속성을 소수만 도입하는 것이 적절하다.

카테고리 enum은 ordinal 저장이다. 기존 ‘운동복’을 삭제·재배열하면 데이터 의미가 바뀔 수 있다. 개편 시 기존 ID/값을 보존하고 마이그레이션을 정의한다. 과거 운동복 항목이 상의인지 하의인지 자동으로 단정하지 않는다.

## 4. 세탁 상태와 기록 신뢰

### ‘깨끗함’과 ‘횟수가 적음’은 다름

현재 상태는 착용 횟수와 세탁 주기로 결정된다. 앱이 실제 오염을 관찰하는 기능은 없다. 횟수를 입력하지 않거나 한 번 입고 얼룩이 생긴 경우, 상태가 실제 옷과 일치한다고 보장할 수 없다. README의 ‘자동 추적’도 사용자가 착용을 수동 기록한다는 전제를 명확히 해야 한다.

권장 방향은 **횟수에 따른 관리 권장**과 **사용자가 바구니에 담아 현재 입을 수 없는 상태**를 구분하는 것이다. 세탁 주기는 개인 설정이고, 관리 방법은 의류의 실제 관리 라벨을 확인해 설정하도록 한다. 구체적인 횟수를 보편적인 세탁 기준처럼 제시하지 않는다.

가방·소품에는 횟수 관리를 끌 수 있어야 하며, 횟수와 상관없이 바구니에 담는 동작을 쉽게 제공한다. ‘바구니에 담기=실제로 세탁이 끝남’이 아니며, 앱의 세탁 완료는 사용자가 완료를 확인한 뒤 기록한다. 세탁소·건조·수선 단계는 타깃 수요가 확인될 때 추가한다.

### 신규 발견: 지난 세탁 전 기록 삭제가 이번 주기까지 변경함

실제 repository 진단에서 다음을 확인했다.

1. 10월 9일 착용 1건 → 10월 10일 세탁 → 10월 11~13일 착용 3건.
2. 세탁 주기는 3회, `totalWears=4`, `wearSinceWash=3`, 상태는 dirty.
3. **10월 9일 기록만 삭제해도 `wearSinceWash=2`, clean으로 변경된다.** 지난 세탁 이후의 착용 이벤트는 여전히 3건이다.
4. 비교 사례로 10월 13일 기록을 삭제하면 지난 세탁 이후 이벤트도 2건이 되어 현재 감소와 일치한다.

[삭제 구현](../../lib/data/repositories/isar_event_repository.dart#L81)은 기록 시점을 확인하지 않고 두 카운터를 모두 감소시킨다. 현재 FR-010b도 같은 규칙을 명시하므로 코드만의 불일치가 아니라 **실 관리 의미를 충분히 반영하지 못한 spec 규칙**이다.

과거 기록 추가·날짜 이동·실행 취소를 넣기 전에 ‘최근 유효 세탁 이후 착용’의 계산 기준을 정리한다. 세탁 전 기록은 총 착용 횟수에는 영향을 주되 현재 주기에는 영향을 주지 않아야 한다. 세탁 취소는 이전 세탁 경계부터 다시 계산해야 하며, 같은 날의 이벤트 순서와 구 데이터의 기록 누락·초기 카운터도 보존하는 정책이 필요하다. 카운터만 무조건 증감하는 방식으로 확장하지 않는다.

## 5. 화면의 역할 재정리

- **홈**: 전체 수·분포 외에 오늘 할 일에 접근한다. ‘오늘 입은 옷 기록’, ‘바구니 N점’, 최근/즐겨찾기 옷을 우선 후보로 둔다. 등록 0점에서는 첫 옷 등록, 소수 등록에서는 그 옷만으로 바로 사용하도록 안내한다.
- **옷장**: 사진과 이름을 먼저 보고, 종류·사용 가능 상태로 좁힌다. 검색·필터의 선택 조건·결과 수·초기화를 한곳에서 확인한다. 모든 태그를 상시 칩으로 늘어놓지 않는다.
- **등록**: 빠른 등록과 상세 편집을 분리한다. 사진이 있으면 기본 이름을 제공하고 이름 없는 사진 등록도 가능하도록 새 spec을 검토한다. 사진이 없으면 짧은 이름을 받는다. 브랜드·구매일·태그·관리 설정은 나중에 보완할 수 있게 한다. 초기 상태도 실제 관리 필요에 맞춰 설정할 수 있게 한다.
- **상세**: 기록 확인과 개별 수정에 집중한다. 매일의 다중 착용 기록이나 바구니 담기를 위해 반드시 들어가는 화면이 되지 않게 한다. 메모 입력은 사용자가 선택했을 때 키보드를 띄운다.
- **세탁**: 실제 바구니에 있는 옷을 선택하고 완료한다. 선택 수, 관리 방법, 처리 대상이 명확해야 한다. 긴 목록에서도 액션에 접근하고, 제외한 옷은 선택·처리 대상에서 빠진다.
- **설정**: 데이터 저장·백업·복원과 실제 지원하는 알림을 명확히 설명한다. 동작하지 않는 기능을 활성 메뉴처럼 제공하지 않는다.

Stylebook은 개별 옷/코디를 날짜에 기록하고, 세탁 중·세탁소·대여 등의 상태와 검색 가능한 속성을 지원한다고 설명한다. 날짜와 현재 사용 가능 상태를 보유 여부와 구분하는 참고 사례다. 해당 서비스의 전체 기능 수를 옷장이모의 목표로 삼지는 않는다. [Stylebook 공식 기능](https://www.stylebookapp.com/features.html)

Whering은 처분한 옷을 활성 목록에서 제외하면서 과거 스타일링 기록은 유지하는 아카이브를 안내한다. 옷장이모에서도 ‘화면 정리’와 ‘기록 완전 삭제’를 별도 의도로 다룰 이유가 있다. [Whering 아카이브 안내](https://whering.co.uk/faq/why-archiving-items)

## 6. 구현 범위를 나누는 제안

### A. 신뢰와 기본 조작성

- 기존 UI 리포트의 선택 잔존·‘기타’ 불일치·큰 글자 overflow 수정.
- 세탁 경계에 따른 착용 카운터 규칙과 테스트 보완.
- 미구현 메뉴·알림 약속 정리, 작은 터치 영역과 오류·로딩 안내 개선.

### B. 실사용 부담을 줄이는 최소 기능

- 빠른/연속 등록, 미분류, 부가 입력 접기.
- 일괄 착용 기록, 날짜 선택, 선택 메모, 실수 취소.
- 사용 가능 필터, 목록에서 바구니 담기/제외, 세탁 방법별 선택.
- 횟수 관리 끄기 및 수동 관리의 의미 정의.

### C. 넓은 배포 전 데이터 보존

- 사용자 실행 백업·복원과 실제 사진·기록·설정 복원 검증.
- 같은 옷과 기록이 중복되거나 일부만 복원되지 않는지 확인.
- 데이터 저장·기기 변경 안내 및 실행 중 실패 처리.

### D. 관찰된 탐색·정리 수요에 따라 확장

- 보관/아카이브, 색상·계절·용도, 일괄 속성 편집.
- 자주 입는 조합, 선택 리마인더, 보관 위치·관리 중 표시.
- 코디 캔버스·AI·구매 통계·콘텐츠는 타깃이 확인될 때 재검토.

개발 기간이나 비용은 산정하지 않았다. 그룹별로 spec을 작성하고 의존성과 검증 범위를 정한 뒤 추정한다. A~C를 마치고 실제 사용자 평가를 해야 넓은 배포를 위한 UX 준비 여부를 판단할 수 있다.

## 7. ‘정말 필요한지’를 확인할 사용자 평가

후속 기능을 결정하기 위한 소규모 평가를 제안한다. 아래 수치와 과제는 목표안이며 현재 달성한 성과가 아니다.

- 참여자 8~12명, 1~2주. 등록·기록을 잘하는 사람만 모집하지 않고, 의류 수가 적고 많은 사람, 기록을 자주 잊는 사람, 운동/출근 의류를 함께 가진 사람, 큰 글자 사용자를 포함한다.
- 처음에는 자주 입는 옷 5~10점만 등록한다. 전체 옷장 등록을 시작 조건으로 요구하지 않는다.
- 첫날: 사진 5점 등록, 사진 없는 옷 1점 등록, 운동용 티셔츠 분류, ‘지금 입을 옷’ 찾기, 세탁 바구니 이용.
- 반복 과제: 하루에 여러 옷 기록, 어제 누락한 착용 추가, 중복 기록 취소, 세탁 전 기록 삭제, 동일 방식의 옷만 세탁 완료.
- 태그 평가: 태그 없는 상태와 최소 선택 속성이 있는 상태에서 같은 옷을 찾게 한다. 순서를 바꾸어 학습 효과를 줄이고, 찾기 시간·성공·분류 혼동·입력 시간을 비교한다.
- 보존 평가: 사용자가 백업을 만들고 별도 빈 테스트 환경에서 사진·옷·기록을 복원한다. 실제 사용자 데이터를 삭제하도록 요구하지 않는다.
- 측정: 등록 완료 시간, 여러 벌 기록 시간, 찾기 성공, 도움 요청, 잘못된 상태 변경, 실제 사용한 태그, 수동 입력 수정, 중단 이유. 둘째 주에는 진행자의 알림 없이 자발적으로 다시 썼는지도 확인한다.
- 제안 목표: 도움 없이 시작 가능, 여러 벌 기록을 30초 안에 수행, 누락·취소를 정확히 복구, 중요한 데이터 복원 누락 0건. 실사용 관찰 후 목표를 조정한다.

외부 분석 SDK는 추가하지 않는다. 동의한 관찰·사용 일지·로컬 진단 자료로 평가한다. 작은 표본의 반복 사용은 개선 방향을 찾는 근거이며, 대중 시장에서의 유지율이나 수요를 통계적으로 증명하지 않는다.

기능 채택 기준은 ‘실제로 반복되는 문제인가’, ‘입력/이동 비용을 줄이는가’, ‘사용자가 결과를 이해하고 신뢰하는가’, ‘기존 로컬 우선 흐름 안에서 유지 가능한가’다. 태그를 더 입력했지만 옷을 더 빨리 찾지 못하거나 기록 빈도가 줄면, 필드 추가보다 기본 탐색·일괄 작업을 다시 개선한다.
