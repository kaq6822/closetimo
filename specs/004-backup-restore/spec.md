# Feature Specification: 사용자 실행형 백업·복원

**Feature Branch**: `feat/issues-batch-20261016` (#40)

**Created**: 2026-10-17

**Status**: Draft

**Input**: GitHub issue #40 — "사용자 실행형 백업·복원으로 옷장 데이터 보존".
기기 변경·앱 재설치 시 등록한 옷, 사진, 착용·세탁 기록, 설정을 복구할 방법이 필요하다.

관련 문서: [data-model.md](./data-model.md)(백업 파일 형식), [contracts/backup-service.md](./contracts/backup-service.md)
(서비스 계약), [plan.md](./plan.md)(패키지·플랫폼 설정).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 백업 파일 만들기 (Priority: P1)

사용자는 설정의 **데이터 백업**에서 백업을 직접 시작해 옷장 전체를 하나의 파일로 만들고,
OS 공유 시트에서 저장 위치(파일 앱·iCloud Drive·Google Drive·메일 등)를 고른다.

**Independent Test**: 옷·사진·기록·설정이 있는 상태에서 백업을 만들고, 생성된 파일을 빈 앱에
복원했을 때 동일한 데이터가 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 옷·사진·착용/세탁 기록이 있는 옷장, **When** 데이터 백업을 실행하면, **Then** 단일 `.zip`
   백업 파일이 만들어지고 OS 공유 시트가 열린다.
2. **Given** 공유 시트가 열린 상태, **When** 사용자가 공유를 취소하면, **Then** 앱 데이터는 변하지 않고
   "백업 저장을 취소했어요" 안내만 표시된다.
3. **Given** 기기 저장 공간이 부족한 상황, **When** 백업을 만들면, **Then** 만들던 파일을 지우고
   "저장 공간이 부족해요" 안내를 표시하며 앱 데이터는 변하지 않는다.

### User Story 2 - 백업에서 복원 (Priority: P1)

사용자는 설정의 **백업에서 복원**에서 OS 문서 선택기로 백업 파일을 고르고, 백업 내용(만든 날짜,
옷 수, 기록 수, 사진 수)과 "현재 옷장을 모두 대체한다"는 안내를 확인한 뒤 복원한다.

**Acceptance Scenarios**:

1. **Given** 새로 설치한 앱, **When** 백업 파일을 골라 복원을 확정하면, **Then** 옷·사진·착용/세탁 기록·
   보관 상태·설정·참조 관계(기록 → 옷)가 백업 시점과 동일하게 보인다.
2. **Given** 파일 선택기 또는 확인 안내, **When** 사용자가 취소하면, **Then** 아무것도 바뀌지 않는다.
3. **Given** 손상된 파일·옷장이모 백업이 아닌 파일, **When** 고르면, **Then** 확인 안내 전에
   "백업 파일을 읽을 수 없어요" 오류를 표시하고 아무것도 바뀌지 않는다.
4. **Given** 이 앱보다 새로운 버전에서 만든 백업, **When** 고르면, **Then** "앱을 최신 버전으로 업데이트한 뒤
   다시 시도해 주세요" 안내와 함께 거부하고 아무것도 바뀌지 않는다.
5. **Given** 같은 백업을 이미 복원한 옷장, **When** 같은 백업을 다시 복원하면, **Then** 옷·기록이 중복되지
   않고 백업과 동일한 상태가 된다(멱등).
6. **Given** 복원 중 저장 공간 부족·쓰기 실패, **When** 복원이 실패하면, **Then** 기존 옷장 데이터와 사진은
   복원 전과 동일하게 남는다(부분 변경 없음).

### Edge Cases

- 백업 시 사진 파일이 사라진 옷(외부 요인으로 sandbox 파일 손실): 사진 없이 백업하고 옷 데이터는 포함한다.
  누락 수를 결과에 포함한다.
- 기록이 존재하지 않는 옷을 가리키는 백업(참조 무결성 위반): 손상으로 간주해 거부한다.
- 같은 id가 두 번 나오는 백업: 손상으로 간주해 거부한다.
- 이미지 엔트리의 CRC가 맞지 않거나 누락: 손상으로 간주해 거부한다.
- 앱이 아는 것보다 높은 `formatVersion`: 거부한다(위 시나리오 2-4). 낮은 버전은 해당 버전 디코더로 읽는다.
- 복원 중 앱 강제 종료: DB는 단일 트랜잭션이므로 이전 상태 또는 복원 완료 상태 중 하나다. 복원용으로
  새로 쓴 사진은 고유한 이름이라 기존 파일을 덮어쓰지 않으며, 커밋 전 종료 시 남는 것은 참조되지 않는
  고아 파일뿐이다(데이터 손상 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 백업과 복원은 **사용자가 설정 화면에서 직접 시작**할 때만 동작한다. 자동·주기 백업, 백그라운드
  업로드는 하지 않는다(헌법 III 로컬 우선).
- **FR-002**: 백업은 **단일 파일 아카이브(zip)** 이며 옷(`Item` 전 필드), 사진, 착용·세탁 기록(`WearEvent`
  전 필드), 설정(`UserPreferences` 전 필드)과 참조 관계(`WearEvent.itemId → Item.id`, 옷 → 사진)를 포함한다.
  형식은 [data-model.md](./data-model.md)를 따른다.
- **FR-003**: 사진은 기기 파일 경로가 아니라 **아카이브 내부 상대 참조**(`images/{itemId}.jpg`)로 기록한다.
- **FR-004**: 백업 파일에는 형식 식별자(`format`)와 **형식 버전**(`formatVersion`)을 둔다. 앱이 지원하는
  최대 버전보다 높으면 복원을 거부한다.
- **FR-005 (복원 정책 = 전체 교체)**: 복원은 현재 옷장 데이터를 **백업 내용으로 전체 교체**한다. 병합하지 않는다.
  근거:
  1. 옷에는 기기 간 안정적인 식별자가 없다(Isar 자동 증가 id). 병합하면 같은 옷이 다른 id로 중복되거나,
     다른 옷이 같은 id로 충돌한다.
  2. `wearSinceWash`·`totalWears`·`status`·`lastWornAt`은 기록에서 파생된 누적값이라 병합 시 이중 집계된다.
  3. 주 사용 사례(기기 변경·재설치)는 빈 옷장에 스냅숏을 그대로 되살리는 것이다.
  4. 전체 교체는 멱등이므로 **같은 백업을 여러 번 복원해도 중복이 생기지 않는다**.
- **FR-006**: 복원 확정 전 백업 정보(만든 날짜, 옷·기록·사진 수)와 현재 옷장 규모, "현재 데이터가 모두
  대체되며 되돌릴 수 없다"는 안내를 보여 주고, 사용자가 명시적으로 확정해야 적용한다.
- **FR-007 (원자성)**: 복원은 다음 순서로 진행하며 어느 단계에서 실패해도 기존 데이터를 부분 변경하지 않는다.
  1. **검증**: 아카이브 구조·JSON·필드 타입·enum 이름·id 중복·참조 무결성·이미지 존재/CRC를 모두 검사한다.
     실패하면 즉시 중단(기존 데이터 무변경).
  2. **이미지 준비(staging)**: 백업 사진을 sandbox `items/`에 **기존 파일과 겹치지 않는 고유 이름**으로 쓴다.
     실패(공간 부족 등)하면 이번에 쓴 파일만 지우고 중단(기존 데이터 무변경).
  3. **커밋**: 단일 Isar 쓰기 트랜잭션에서 옷·기록·설정을 비우고 백업 내용으로 채운다. 실패하면 트랜잭션이
     롤백되고 2단계에서 쓴 파일을 지운다.
  4. **정리**: 커밋 후 이전 옷들의 사진 파일을 best-effort로 지운다(실패해도 데이터 정합성에는 영향 없음).
- **FR-008**: 실패 유형별로 구분된 안내를 표시한다: 취소(무변경 안내), 손상 파일, 지원하지 않는 버전,
  저장 공간 부족, 그 밖의 파일 오류.
- **FR-009 (플랫폼 흐름)**: 앱은 클라우드 API를 직접 호출하지 않는다. 클라우드 저장은 OS가 제공하는 UI를
  경유한 사용자 선택으로만 이뤄진다.
  - **iOS 백업**: 앱 임시 디렉터리에 파일 생성 → `UIActivityViewController`(공유 시트) → 사용자가
    "파일에 저장"에서 iCloud Drive/나의 iPhone 등 위치 선택, 또는 AirDrop·메일 등.
  - **iOS 복원**: `UIDocumentPickerViewController`(파일 앱 선택기) → iCloud Drive·나의 iPhone 등에서 선택.
    iCloud에만 있는 파일은 OS가 내려받아 앱에 사본을 넘긴다.
  - **Android 백업**: 앱 캐시 디렉터리에 파일 생성 → `ACTION_SEND` 공유 시트(FileProvider URI) → 사용자가
    Google Drive·파일 앱·메일 등 선택.
  - **Android 복원**: Storage Access Framework 문서 선택기(`ACTION_OPEN_DOCUMENT`) → Google Drive·
    다운로드 등에서 선택. 선택된 문서는 앱 캐시로 복사해 읽는다.
  - 두 플랫폼 모두 **저장소·사진 권한을 요청하지 않는다**(공유 시트·문서 선택기는 사용자 선택 단위 접근).
- **FR-010**: 복원 후 화면은 Isar 스트림으로 자동 갱신된다. 앱 재시작은 필요 없다.
- **FR-011**: 직렬화는 Isar 모델을 리플렉션 없이 명시적으로 매핑하고, 매핑은 `lib/data/backup/backup_codec.dart`
  한 곳에 모은다. 모델에 필드가 추가되면 필드 목록 가드 테스트가 실패해 codec 갱신을 강제한다.
- **FR-012**: 백업 형식에 필드를 추가하거나 의미를 바꾸면 `formatVersion`을 올리고 이전 버전 디코더를 유지한다
  ([data-model.md §4](./data-model.md#4-버전-정책)).

### Key Entities

- **백업 아카이브**: zip 파일 1개. `backup.json` + `images/*`.
- **ValidatedBackup**: 검증을 통과한 백업의 미리보기(메타·개수)와 파일 위치. 확인 안내와 적용에 쓰인다.

## Success Criteria *(mandatory)*

- **SC-001**: 백업 → 빈 DB 복원 후 옷(전 필드)·사진 바이트·기록·설정이 원본과 동일하다(통합 테스트).
- **SC-002**: 취소·손상 파일·높은 버전·공간 부족·중복 복원 경로 모두에서 기존 데이터가 변하지 않거나
  (중복 복원의 경우) 백업과 동일한 상태가 된다(단위·통합 테스트).
- **SC-003**: 새 Isar 필드가 추가되면 가드 테스트가 실패한다.
- **SC-004**: 네트워크 권한·클라우드 SDK 없이 동작한다.

## Assumptions

- 백업 파일은 암호화하지 않는다. 사용자가 고른 저장 위치의 보안(iCloud/Drive 계정)을 따른다. 안내 문구로
  "백업 파일에는 옷 사진과 기록이 들어 있어요"를 표시한다.
- `StorageMetadata`(기기 저장소 이전 상태)는 백업 대상이 아니다. 복원 기기의 값을 유지한다.
- 휴대폰 폼팩터 한정이므로 iPad 공유 시트 위치(popover anchor)는 고려하지 않는다.
