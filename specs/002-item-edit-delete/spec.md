# Feature Specification: 옷 정보 수정 & 삭제

**Feature Branch**: `002-item-edit-delete`

**Created**: 2026-07-04

**Status**: Draft

**Input**: User description: "옷 수정,삭제 기능 구현"

## 배경

v1 MVP(001-home-dashboard)는 옷 등록·탐색·착용 기록·세탁·홈 대시보드를 제공하지만,
**한번 등록한 옷의 정보를 고치거나 옷장에서 완전히 지우는 흐름이 없다.** `ItemRepository`에는
`create`만 있고 `update`/`delete`가 없으며, 상세 화면 우상단 휴지통 아이콘은 v1에서 비활성으로
남겨져 있었다(001 tasks T054 주석). 오타 수정, 사진 교체, 세탁 주기 조정, 처분한 옷 정리가
불가능해 실사용 시 가장 먼저 부딪히는 공백이다. 본 feature는 이 두 흐름을 채운다.

## Clarifications

### Session 2026-07-04

- Q: 수정 화면에서 편집 가능한 필드는? → A: 등록 시 입력하는 필드 전부(사진·명칭·브랜드·카테고리·세탁 주기·세탁 방법·구매일). 파생 값(세탁 후 착용 횟수·총 착용 횟수·상태·마지막 착용일·마지막 세탁일)은 편집 대상이 아니다 — 이벤트 기록으로만 변한다.
- Q: 세탁 주기를 수정하면 청결 상태를 어떻게 처리할까? → A: 저장 시 즉시 재평가한다. `wearSinceWash >= washCycle`이면 `dirty`, 아니면 `clean`. 예: `wearSinceWash=4`인 옷의 주기를 10→3으로 낮추면 즉시 `dirty`, 3→10으로 높이면 `clean`으로 복귀.
- Q: 수정·삭제 진입점은? → A: 옷 상세 화면 상단바 우측 오버플로 메뉴(⋯)에 "수정하기"·"삭제하기"를 둔다. 기존 비활성 휴지통 아이콘을 대체한다.
- Q: 옷을 삭제하면 연관 데이터는? → A: 해당 옷의 모든 착용·세탁 이벤트(`WearEvent`)와 sandbox 이미지 파일을 함께 제거한다. 세탁 바구니에 담겨 있었다면 바구니에서도 사라진다(`inLaundry`는 Item의 필드이므로 Item 삭제로 함께 소멸).
- Q: 삭제 확인은? → A: 되돌릴 수 없는 파괴적 동작이므로 확인 다이얼로그를 반드시 거친다. 확정 후 옷장 탭으로 복귀한다.
- Q: 사진 교체·제거를 허용할까? → A: 둘 다 허용한다. 새 사진 선택 시 sandbox 사본을 교체하고, "사진 제거" 시 기본 플레이스홀더로 되돌린다(파일 삭제 + `imagePath=null`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 옷 정보 수정 (Priority: P1)

사용자는 이미 등록한 옷의 상세 화면에서 "수정하기"로 진입해 사진·명칭·브랜드·카테고리·세탁 주기·세탁 방법·구매일을 고치고 저장한다. 저장 즉시 옷장 그리드와 상세 화면에 변경이 반영된다.

**Why this priority**: 잘못 입력한 이름·카테고리·세탁 주기를 고칠 수 없으면 데이터 신뢰가 무너진다. 삭제보다 자주 일어나고, 삭제 없이도 단독으로 가치를 전달한다.

**Independent Test**: 옷 1점을 등록한 뒤 상세 → "수정하기" → 명칭을 "수정된 코트"로 바꾸고 세탁 주기를 +2 한 뒤 저장 → 상세·옷장 그리드에 새 값이 노출되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 명칭 "코트", 세탁 주기 5인 옷의 수정 화면이 열려 있다, **When** 명칭을 "겨울 코트"로 바꾸고 "수정 완료"를 누른다, **Then** 상세 화면 제목과 옷장 타일 이름이 "겨울 코트"로 갱신되고 토스트로 "옷 정보를 수정했어요"가 노출되며 착용 횟수·상태는 그대로 유지된다.
2. **Given** 수정 화면에서 명칭 필드를 모두 지웠다, **When** 저장 버튼을 본다, **Then** 상단 "저장"과 하단 "수정 완료" 버튼이 비활성(흐림) 상태로 클릭이 무시된다(등록과 동일 규칙).
3. **Given** 세탁 후 착용 횟수 4회, 세탁 주기 10, 상태 `clean`인 옷의 수정 화면이다, **When** 세탁 주기를 3으로 낮춰 저장한다, **Then** 저장 즉시 상태가 `dirty`로 전환되어 옷장 그리드에 "세탁 필요" 라벨이 표시된다.
4. **Given** 세탁 후 착용 횟수 5회, 세탁 주기 5, 상태 `dirty`인 옷의 수정 화면이다, **When** 세탁 주기를 8로 올려 저장한다, **Then** 상태가 `clean`으로 복귀한다.
5. **Given** 사진이 있는 옷의 수정 화면이다, **When** 사진 카드를 탭해 새 사진을 선택하고 저장한다, **Then** 상세·옷장의 사진이 새 사진으로 교체된다. **When** "사진 제거"를 선택하고 저장하면, **Then** 기본 플레이스홀더로 되돌아간다.

### User Story 2 - 옷 삭제 (Priority: P2)

사용자는 옷장에서 처분했거나 잘못 등록한 옷을 상세 화면에서 완전히 삭제한다. 삭제된 옷은 옷장·홈·세탁 어디에서도 사라지고, 그 옷의 착용·세탁 기록과 사진 파일도 함께 제거된다.

**Why this priority**: 착용-세탁 사이클을 닫는 것과 별개로, 옷장을 실제 소유 목록과 일치시키는 유지보수 흐름이다. P1(수정)이 없으면 삭제만으로는 반쪽이므로 P2.

**Independent Test**: 착용 기록이 있는 옷을 상세에서 "삭제하기" → 확인 → 옷장 그리드에서 사라지고, 홈 통계 전체 수가 1 감소하며, 같은 이름으로 재진입할 상세가 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 옷장에 옷 3점이 있고 그 중 1점의 상세 화면이 열려 있다, **When** 오버플로 메뉴에서 "삭제하기"를 누르고 다이얼로그에서 "삭제"를 확정한다, **Then** 해당 옷이 옷장 그리드에서 제거되고 자동으로 옷장 탭으로 복귀하며 토스트로 "옷을 옷장에서 삭제했어요"가 노출된다. 홈 통계 전체 수는 3→2가 된다.
2. **Given** 삭제 확인 다이얼로그가 떠 있다, **When** 사용자가 "취소"를 누른다, **Then** 아무것도 삭제되지 않고 상세 화면으로 돌아간다.
3. **Given** 착용 이벤트 2건과 세탁 이벤트 1건이 있는 옷을 삭제한다, **When** 삭제가 완료된다, **Then** 그 옷의 `WearEvent` 3건이 모두 제거되어 어떤 화면·통계에도 잔존하지 않는다.
4. **Given** 세탁 바구니에 담긴(`inLaundry=true`) 옷을 삭제한다, **When** 삭제가 완료된다, **Then** 세탁 탭 바구니 목록과 홈 세탁 미리보기에서도 해당 옷이 사라진다.
5. **Given** 사진이 등록된 옷을 삭제한다, **When** 삭제가 완료된다, **Then** sandbox의 이미지 파일(`items/{id}.jpg`)도 함께 제거된다.

### Edge Cases

- 수정 화면 진입 후 아무것도 바꾸지 않고 저장하면, 변경 없는 저장으로 처리되어 값·상태가 그대로 유지된다(에러 없음).
- 수정 중 시스템 back(또는 백버튼)으로 나가려 할 때 변경 사항이 있으면 "작성을 그만두시겠어요?" 확인 다이얼로그를 띄운다(등록 화면과 동일 규칙).
- 존재하지 않는 `id`로 수정·삭제를 시도하면(예: 이미 삭제된 옷) 조용히 무시하고 이전 화면으로 복귀한다.
- 세탁 주기를 1 미만으로 낮추려 하면 스테퍼가 최소값 1로 가드한다(등록과 동일).
- 이미지 파일 삭제가 실패해도(파일이 이미 없음 등) DB 레코드 삭제는 성공으로 간주하고 흐름을 진행한다(파일 삭제는 best-effort).
- 삭제는 되돌릴 수 없다. v1 범위에서 실행 취소(undo)는 제공하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**옷 정보 수정 (US1)**

- **FR-001**: 시스템은 옷 상세 화면에서 "수정하기" 진입점을 제공해야 하며, 진입 시 해당 옷의 현재 값(사진·명칭·브랜드·카테고리·세탁 주기·세탁 방법·구매일)이 폼에 미리 채워져야 한다.
- **FR-002**: 시스템은 명칭·브랜드·카테고리·세탁 주기·세탁 방법·구매일·사진을 편집해 저장할 수 있어야 한다. 세탁 후 착용 횟수·총 착용 횟수·상태·마지막 착용일·마지막 세탁일은 수정 폼에서 편집 대상이 아니다.
- **FR-003**: 명칭이 비어 있는 동안 "저장"·"수정 완료" 버튼은 비활성 상태여야 한다(등록 FR-002와 동일 규칙).
- **FR-004**: 세탁 주기를 수정해 저장하면 시스템은 상태를 즉시 재평가해야 한다 — `wearSinceWash >= washCycle`이면 `dirty`, 아니면 `clean`.
- **FR-005**: 사진 수정은 (1) 새 사진 선택 시 sandbox 사본을 교체하고, (2) "사진 제거" 시 파일을 삭제하고 `imagePath=null`(기본 플레이스홀더)로 되돌려야 한다.
- **FR-006**: 저장 성공 시 옷장 그리드·상세 화면·홈 통계가 즉시 새 값을 반영하고 비차단 토스트("옷 정보를 수정했어요")를 노출해야 한다.
- **FR-007**: 수정 화면에서 변경 사항이 있는 채로 back을 시도하면 확인 다이얼로그를 띄워야 한다(등록 화면과 동일).

**옷 삭제 (US2)**

- **FR-008**: 시스템은 옷 상세 화면에서 "삭제하기" 진입점을 제공해야 한다.
- **FR-009**: "삭제하기"는 되돌릴 수 없는 파괴적 동작이므로 확인 다이얼로그(삭제/취소)를 반드시 거쳐야 한다.
- **FR-010**: 삭제 확정 시 시스템은 단일 트랜잭션으로 (1) 대상 `Item` row와 (2) 같은 `itemId`를 가진 모든 `WearEvent`(kind 무관: wear·wash 모두)를 제거해야 한다.
- **FR-011**: 삭제 시 해당 옷의 sandbox 이미지 파일(`items/{id}.jpg`)을 제거해야 한다. 파일이 없거나 삭제에 실패해도 DB 삭제 결과에는 영향을 주지 않는다(best-effort).
- **FR-012**: 삭제 완료 후 사용자는 옷장 탭으로 복귀하고, 비차단 토스트("옷을 옷장에서 삭제했어요")가 노출되어야 한다. 삭제된 옷은 옷장·홈 통계·세탁 바구니 어디에도 잔존하지 않아야 한다.

**전역 / 비기능 (Cross-cutting)**

- **FR-013**: 수정·삭제 모든 동작은 네트워크 없이 로컬 Isar 트랜잭션으로만 수행되어야 한다(헌법 III, 001 FR-025와 정합).
- **FR-014**: 수정 화면 UI는 등록 화면과 동일한 디자인 토큰·위젯(001 FR-024)을 재사용해야 한다. 별도 색상·간격·라운딩을 도입하지 않는다.

### Key Entities

- **Item**: 001과 동일. 본 feature는 스키마 필드를 추가하지 않는다. 수정은 기존 필드 값을 변경하고, 삭제는 row를 제거한다.
- **WearEvent**: 001과 동일. 삭제 시 대상 Item의 모든 이벤트가 함께 제거된다(cascade). 스키마 변경 없음.
- **ItemPatch (신규, 영속화 대상 아님)**: 수정 폼이 repository에 전달하는 변경 요청 값 객체. 필드 — name, brand, category, careMethod, washCycle, purchasedAt + 사진 의도(새 파일 / 제거 / 유지). Isar 컬렉션이 아니라 in-memory DTO다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 옷 상세에서 3단계(⋯ → 수정하기 → 필드 수정 후 저장) 이내로 정보를 고칠 수 있다.
- **SC-002**: 수정 저장 후 100ms 이내에 옷장 그리드·상세 화면이 새 값을 반영한다(001 SC-003과 동일 기준).
- **SC-003**: 옷 삭제 후 옷장·홈 통계·세탁 바구니에서 100% 즉시 제거된다(잔존 0건).
- **SC-004**: 삭제된 옷의 착용·세탁 이벤트가 DB에 잔존하지 않는다(orphan 이벤트 0건).
- **SC-005**: 수정·삭제 모든 핵심 동작이 네트워크 차단 상태에서 정상 동작한다.

## Assumptions

- 실행 취소(undo)와 휴지통(soft delete)은 v1 범위 밖이다. 삭제는 즉시 영구 삭제한다.
- 다중 선택 일괄 삭제(옷장 그리드에서 여러 옷 선택 후 삭제)는 본 feature 범위 밖이다. 단건 삭제만 다룬다.
- 수정 이력(누가 언제 무엇을 바꿨는지) 추적은 범위 밖이다. 단일 사용자 로컬 앱 특성상 불필요.
- 수정 화면은 기존 등록 화면(`AddItemScreen`)의 폼을 재사용해 모드(등록/수정)만 분기한다. 별도 화면 신설을 지양한다(헌법 I·II).
